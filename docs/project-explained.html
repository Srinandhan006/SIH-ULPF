00What it does

The problem

A pipeline parses a log only after a person writes a parser for that exact format. A new device, or a vendor update that changes one field, gets dropped, stored as raw text, or silently misread.

What we built

Every log is tried against 7 ladders of increasing effort. Each result carries a tier (which ladder produced it) and a confidence (0 to 1), so consumers filter by trust.

The guarantee

1 log line in = exactly 1 stored raw record + exactly 1 stored event. No exception, no drop.

AnalogyAirport customs that never refuses entry. Every passenger is admitted. The officer only decides how much they can vouch for, and writes that on the passenger's file.

01Architecture

A log reaches the API. In demo mode the API parses it. In production the API queues it and workers parse it. Both write to the same two stores.

  1. Collector (Go, port 5514)Receives syslog over UDP and TCP, or tails a file. Groups lines into batches (200 per source, or every 500 ms) and POSTs them to the API. It never parses content and never knows workers exist.
  2. API (Python FastAPI, port 8080)The front door for writing and reading. Accepts POST /v1/ingest, serves events, drift, unknown clusters, metrics and the /docs page.
  3. Redis StreamA numbered waiting line. Used only in production mode.
  4. WorkersPython processes that pull logs from the line and run the engine. They open no port. They only call out to Redis.
  5. Parse engineRuns the 7-tier ladder on each log, checks drift, records unknown formats, converts the result to the OCSF standard schema.
  6. StorageSQL database for parsed events (SQLite in demo, PostgreSQL in production). Raw store for the original bytes, kept forever, addressed by SHA-256.
AnalogyCollector = mailroom clerk who bundles letters and never reads them. API = front desk. Redis = the numbered ticket line. Workers = cashiers. Engine = the customs officer. Storage = the archive room plus the index cards.

02Demo vs production

Today's demo runs in ULI_MODE=local. Production uses ULI_MODE=distributed and more workers.

DEMO what is toggled now

docker-compose.yml line 27: the api service has ULI_MODE: local.

The API parses inline, so inject.sh prints the tier instantly. The 2 workers run and stay idle.

PRODUCTION what changes

Set ULI_MODE: distributed on the api service. The API queues every log and replies queued: true. Workers parse.

Kubernetes manifests already use distributed for both API and workers.

Commands

# demo: what you run today
docker compose up -d

# production on Docker Compose: set ULI_MODE: distributed under the api service, then
docker compose up -d --scale worker=8

# production on Kubernetes (API already distributed)
kubectl scale deployment uli-worker --replicas=8 -n uli

# see how many workers run
docker compose ps

In distributed mode inject.sh prints an error line, because the API returns no event id yet. The log is still queued and a worker parses it. Read the result from GET /v1/events.

03Who gives each worker its logs?

Nobody assigns them. The collector never talks to workers. Workers pull, and Redis hands each log to exactly one worker.

AnalogyA bakery with one numbered ticket line and several cashiers. A cashier calls "next!" when free. The line never chooses a cashier.
  • Pull, not push. A worker asks Redis for the next batch (XREADGROUP, up to 200 logs, waits 1 second if none). Redis marks those logs "in flight" for that worker.
  • Done = XACK. The worker stores the events, then acknowledges. Unacknowledged logs stay in flight.
  • Crash recovery. When a worker restarts under the same name, it re-reads its own in-flight logs first.
  • Proof we ran. 40 tagged logs sent in distributed mode. Redis showed 2 separate consumers, both at 0 pending. The events table grew by exactly 40: none lost, none duplicated.

LIMIT No other worker takes over a dead worker's in-flight logs (no XAUTOCLAIM). A container recreated under a new name leaves its in-flight logs orphaned.

04After you paste a log in inject.sh, where is it?

Yes, in the database: data/uli.db, table events. The original bytes are in data/raw/.

1 · Your terminal (instant)

inject.sh prints tier, confidence, parser and the message.

2 · The database file

Open data/uli.db with the VS Code "SQLite Viewer" extension. Table events: event_id, source_id, tier, confidence, parser_id, message, body. body is the full OCSF JSON.

3 · The API

Filter by your source: GET /v1/events?source_id=vscode-demo. One event with its full OCSF JSON: GET /v1/events/<event_id>. Commands below.

4 · The browser

Open http://localhost:8080/docs. Click GET /v1/events, then "Try it out".

5 · The original bytes

GET /v1/raw/<raw_event_id> returns the exact line and a SHA-256 check. Or open the file under data/raw/default/<source>/<date>/.

6 · Unrecognized lines

Tier 4 and worse also appear in table unknown_clusters and at GET /v1/unknown.

curl -s "localhost:8080/v1/events?source_id=vscode-demo" | jq '.[] | {tier: .provenance.tier, confidence: .provenance.confidence, parser: .provenance.parser_id, message}'
curl -s localhost:8080/v1/events/<event_id> | jq

05The API and ports

Two doors face the outside: 8080 (HTTP) and 5514 (syslog). Everything else stays inside the Docker network.

8080
API · HTTP

Write: POST /v1/ingest. Read: /v1/events, /v1/sources, /v1/unknown, /v1/drift, /v1/parsers, /v1/stats. Ops: /health, /metrics, /docs.

5514 udp+tcp
Collector · syslog in

Only started with --profile collector. TCP handles octet-counted and newline framing.

6379
Redis · queue

API (distributed mode) and workers connect here. Nothing else needs it.

8090
ML sidecar

Optional. Off by default. Only --profile ml starts it.

AnalogyOne building. A front door (8080), a mail slot (5514), and a staff corridor (the Docker network) where the cashiers walk to the ticket line (6379).

06Redis and Redis Streams

Redis is an in-memory database. Here it is only the waiting line between the API and the workers. It stores no results.

AnalogyRedis is the whiteboard at the bakery. A Stream is the numbered ticket roll pinned to it: tickets are added at the end, each has an increasing id, and nothing is erased when a cashier takes one.

Where it is "installed"

Nowhere separate. Streams are a built-in Redis feature. The redis service in docker-compose.yml runs the stock redis:7-alpine image. Our code in uli/ingestion/queue.py (RedisStreamsQueue) calls its stream commands.

Our settings

Stream uli:raw · group uli-workers

Cap ≈ 1,000,000 entries (stream_maxlen)

Batch 200 · wait 1000 ms

Fallback: if Redis is unreachable, an in-process memory queue is used (single process only).

The four commands we use

# once: create the shared group (and the stream if missing)
XGROUP CREATE uli:raw uli-workers 0 MKSTREAM

# API, per log: append the log envelope; trim to ~1,000,000
XADD uli:raw MAXLEN ~ 1000000 * e '{...json envelope...}'

# worker, in a loop: take up to 200 unread logs, wait up to 1 s
XREADGROUP GROUP uli-workers <worker-name> COUNT 200 BLOCK 1000 STREAMS uli:raw >

# worker, after storing the events: confirm
XACK uli:raw uli-workers <id> <id> ...

Check it yourself

docker exec uli-redis-1 redis-cli XLEN uli:raw
docker exec uli-redis-1 redis-cli XINFO GROUPS uli:raw
docker exec uli-redis-1 redis-cli XINFO CONSUMERS uli:raw uli-workers
  • LIMIT Redis runs with persistence off (--save "" --appendonly no). A Redis restart loses logs still waiting in the stream. Production fix: --appendonly yes.
  • depth in /health is the stream length, not the backlog. Acknowledged entries stay until trimmed.

07The 7 tiers

A cascade, not a checklist. A clean log stops after tiers 1-3. Only weak results fall further.

Drain3 is not machine learning

It is a deterministic clustering algorithm. It sorts lines by token count, walks a fixed-depth tree on the first tokens, and merges a line into a template when 40% or more of the tokens match. Differing tokens become <*>. No training data, no weights. We mask IPs, numbers and timestamps first so grouping is stable. One tree per source.

The only real ML

Tier 6 only, optional. Isolation Forest scores outliers. Nearest Centroid guesses the closest vendor shape. Both train live in milliseconds on local traffic. No GPU, no download. They annotate; they never decide.

AnalogyCustoms again. Tier 1: "your passport has a valid layout." Tier 2: "I have your country's exact rulebook." Tier 3: "I check your bag whoever you are." Tier 4: "I have never seen this passport, but 50 like it came through today." Tier 7: "Unknown. Admitted, tagged, and flagged for a supervisor."

08How drift is detected

Two detectors and one link. Format drift watches the logs. Infrastructure drift watches the machine. The link says if one explains the other.

Format drift

  1. Per source and parser, collect a window: 200 logs or 60 seconds.
  2. Count the shape fingerprints in the window. Compare with the reference window using Jensen-Shannon divergence.
  3. Above 0.25, or average confidence down by more than 0.15, in 2 windows in a row: fire a drift event. The source is marked degraded.

One odd window is ignored. Stored in parser_drift_events.

Infrastructure drift

  1. Every 30 seconds each worker reads deployment/desired-state.yaml.
  2. It compares with the real CPU count, memory, container image IDs and ULI_* variables.
  3. Any mismatch becomes a row in drift_events, with a pointer to the snapshot.

An empty file means no checks and no false alarms.

The link

When format drift fires, we look back 900 seconds. Any infrastructure drift in that window is listed in explained_by.

Repair: Needleman-Wunsch aligns the old template against the new one and carries field labels across. Today that runs on demand for known parsers.

AnalogyFormat drift: a colleague changed their handwriting. Infrastructure drift: the office changed its locks. The link is the detective asking whether the two happened the same afternoon.

Live proof, one command

Sends 400 logs of one JSON shape, then 400 of another, all parsed by the same parser. Expect js_divergence: 1.0.

SRC=drift-$RANDOM
for shape in A A B B; do
python3 - "$shape" "$SRC" <<'PY' | curl -s -X POST localhost:8080/v1/ingest -H 'Content-Type: application/json' -d @- >/dev/null
import json, sys
shape, src = sys.argv[1], sys.argv[2]
if shape == "A":
    mk = lambda i: {"level": "info", "msg": "request completed", "host": f"h{i%5}", "status": 200}
else:
    mk = lambda i: {"level": "warn", "event": "disk_pressure", "node": f"n{i%5}", "pct_used": 92, "threshold": 90, "mount": "/data"}
print(json.dumps({"source_id": src, "lines": [json.dumps(mk(i)) for i in range(200)]}))
PY
done
curl -s localhost:8080/v1/drift/parsers | jq --arg s "$SRC" '[.[] | select(.source_id==$s)][0] | {source_id, parser_id, js_divergence, reason}'

Infrastructure drift proof: uncomment cpu_count: 999999 in deployment/desired-state.yaml, run docker compose restart api worker, wait 30 seconds, then curl -s "localhost:8080/v1/drift?kind=cpu" | jq. It reports desired 999999, observed 10 (your CPU count). Re-comment the line afterwards.

09Numbers

One worker parses about 500 logs per second. Measured, not estimated.

~500
logs per second per worker (485 to 555 across runs)
~2 ms
per log inside a batch; 4-5 ms for a log sent alone
495
logs per second across 1,000 mixed sources
200
logs per batch, per pull
1M
entries the Redis line holds before trimming
~23 d
for 1 billion logs on one worker: add workers

Measured on a 10-logical-CPU laptop, SQLite, batches of 200, up to 100,000 logs. Batching the database writes made it 2.6× faster than the earlier per-log writes (~210 logs per second).

  • Sources: no cap in the code. 1,000 distinct sources tested with exact per-source counts.
  • Scale: more workers, each pulling its own slice of the Redis line. Then PostgreSQL instead of SQLite.
  • Not measured: throughput with N workers, and runs above 100,000 logs. Linear scaling is the design, not a measured result.
AnalogyOne cashier scans about 500 items a second. Ten cashiers on the same line are designed for about 5,000, but we have timed only one.

11What is unique, and what is not

1 · Offline parser repair

A drifted parser is repaired with sequence alignment (Needleman-Wunsch, from DNA analysis). No LLM, no cloud call.

2 · One timeline for two kinds of drift

Infrastructure changes and format changes share one store and one provenance model, and are linked by explained_by. Proven by a passing end-to-end test.

3 · Air-gapped by construction

Zero external URLs in the runtime package. Vendor packs and offline bundles can be Ed25519-signed.

Not our invention, stated up front: format-drift detection (Cisco/Splunk patent), quarantine plus AI-suggested parsers (Databahn), OCSF, Drain3, Isolation Forest, JS divergence.

Known limits: say these before a judge finds them

  • COLLECTOR After 5 failed sends (about 6 seconds of API downtime) it drops that batch. Its own comment says it never drops.
  • COLLECTOR transport is empty on batches flushed by the timer. UDP source ids include the sender's port, so a device that changes ports looks like several sources.
  • REDIS Persistence is off; a restart loses waiting logs. No takeover of a dead worker's in-flight logs.
  • SCALE No CPU or memory limits on containers. No autoscaler. Multi-worker throughput and runs above 100,000 logs are unmeasured.
  • SECURITY Static API keys only, no TLS, no rate limit. Signature checking is opt-in (ULI_BUNDLE_REQUIRE_SIGNATURE). Redis port is published on the host.
  • DRIFT A successor parser is not proposed automatically when a known parser drifts; it runs on demand.

13Glossary

Log / event
A log is one raw line. An event is its parsed, graded, stored form. 1 log = 1 event.
Tier
Which of the 7 ladders produced the result. Lower is more certain.
Confidence
0 to 1 trust score. Under 0.6 the log keeps falling down the ladder.
OCSF
Open Cybersecurity Schema Framework: one shared set of field names every parsed log is mapped to.
Provenance
The paper trail on each event: raw bytes hash, parser and version, tier, confidence.
Template
A log's fixed skeleton with variable parts replaced by wildcards.
Drift
Something that used to be stable changed shape: a log format or the machine's setup.
Consumer group
A set of workers sharing one Redis stream; each entry goes to exactly one member.
XACK
A worker telling Redis "this entry is finished".
Air-gapped
Runs with no internet at any point.
