Universal Log Intelligence

A vendor-agnostic log pipeline that maps any log format onto OCSF 1.9 — and keeps producing a traceable event even for a vendor it has never seen before.

92 / 92 tests passing 4 / 4 containers healthy 2 real bugs found & fixed by live testing 12 real datasets, 0 synthetic fixtures report generated 2026-09-06
The problem

Every log pipeline works — until it meets a format it hasn't seen

Production pipelines normalize a log only after a human has written a parser for that exact format. A new vendor, a new firmware version, or a silently changed log line either gets dropped, gets stored as useless raw text, or — worse — keeps being parsed by a stale rule and produces confidently wrong data. Universal Log Intelligence (ULI) is built around one non-negotiable rule instead: a line that fails every deterministic tier still produces a usable, traceable event — never an exception, never a silent drop.

This page walks through how that actually works in the code that exists today (not a design doc — every claim below points at a file, a test, or a number that was measured on this machine), how to demonstrate it yourself in under five minutes, and — since that was asked directly — an honest answer on scalability and on what is still left to do.

The direct answer

Is it scalable?

Yes, horizontally — and the single-process ceiling is measured and published, not hidden.

What was measured

One unbatched Python process sustains 177–216 events/sec with sub-11 ms p99 latency up to 100,000 events, using flat memory. This is the floor, not the ceiling — see measured performance.

What was built and run

A distributed topology — 2 worker containers pulling from one Redis Streams queue behind a shared API — was actually built, started, and verified functionally correct in this session, not just diagrammed. See horizontal scaling.

The honest caveat: the per-worker number is CPU-bound on SQL statement overhead (profiled, not guessed — § where the time goes), and a quantified "events/sec vs. worker count" curve was not benchmarked in this build. The scaling mechanism is demonstrated; its throughput curve is not yet measured. That gap is stated plainly rather than papered over with a projected number.

Architecture

How it works, end to end

One line enters as bytes; it leaves as an OCSF-shaped event that always points back at the exact bytes it came from.

Every component here is something this build actually starts and talks to: uli/api/app.py (FastAPI), Redis Streams, uli/workers/runner.py, uli/engine.py + uli/pipeline.py (the ladder), and uli/storage/sql.py (SQLAlchemy Core over SQLite or PostgreSQL). The Go collector (collector/cmd/uli-collector) is a dumb, static-binary forwarder — it does no parsing, so it can sit at the network edge with a minimal attack surface (17.9 MB distroless image, see deployment topologies).

The core mechanism

The 7-tier parsing ladder

Every tier is a total function — it returns a result, it never raises. If a tier can't parse a line with confidence, it says so and the next tier gets a turn. Nothing ever reaches "no event was produced."

TierStrategyConfidenceWhat it actually does
1Structural0.6 – 0.8Recognizes JSON, CEF, LEEF, syslog 5424/3164, logfmt/KV, Common Log Format, log4j — formats with a fixed grammar, no vendor knowledge needed.
2Declarative vendor pack0.85 – 1.0A YAML file in parsers/vendors/ with a signature + regex/grok field extraction. Hot-loaded — no rebuild, no restart.
3Field / type inference+0.05 – 0.15Always runs to enrich tiers 1 and 4 with typed field guesses (IP, port, timestamp, integer…).
4Drain3 template mining0.4 – 0.6Online clustering into a wildcarded template (e.g. id <NUM> state RUNNING) when no declarative pack matches.
5Shape similarity0.3 – 0.7Compares the line's structural fingerprint against known shapes even when the exact template hasn't been mined yet.
6ML sidecar (optional)additiveIsolation-Forest anomaly score + nearest-centroid vendor guess. Annotation only — see § ML sidecar.
7Quarantine≤ 0.3The floor. Raw bytes, fingerprint, and best-effort template are preserved — nothing is thrown away.

A line only falls into the unknown-vendor registry (next section) when it lands at tier ≥4 and confidence stays below tau_known (0.6 by default) — a threshold, not a guess: it was the exact bug found and fixed in this build (the gate originally only fired at tier ≥6, silently skipping Drain3-tier unknowns; corrected against the project's own architecture spec, regression-tested in tests/integration/test_unknown_and_evolution.py).

Self-improving, human-approved

Unknown-vendor learning loop

A format nobody configured doesn't just get quarantined forever — it gets clustered, and after enough examples, ULI drafts a parser for it.

The suggestion step reuses the same template-alignment machinery as parser-drift evolution (next section) rather than a second implementation — for a fresh vendor there's simply no v1 pack to align against, so the alignment runs against nothing and the draft comes straight from inferred field types. Promotion is never automatic: a suggestion sits at GET /v1/parsers/suggestions until a human calls POST /v1/parsers/suggestions/{id}/promote with approved_by recorded for audit — an auto-promoted parser trained on 20 lines from one cluster could start misrouting superficially similar traffic, so the loop deliberately keeps a person in it.

Resilience, not brittleness

Parser-drift resilience

A vendor doesn't announce when it changes its log format. ULI is built to keep every event flowing through the change, and to notice the change happened.

A real example, run against the live stack in this session

v1 (known format):  Jun 14 15:16:01 host1 myapp[555]: connection accepted from 10.0.0.5
v2 (drifted format): Jun 14 15:17:02 host1 myapp(555): INFO connection accepted from 10.0.0.6

The bracket became parentheses and a severity token was inserted. Both lines produced a usable, tiered event — tests/e2e/test_deployed_stack.py::test_format_drift_does_not_break_ingestion and scripts/demo.py scenario 2 both assert this against the real deployed container, not a mock.

Detection works statistically, not by string diffing: per (source_id, parser_id), ULI keeps a rolling window (default 500 events / 60s) of the structural-shape histogram and mean confidence, and compares it to a frozen reference window via Jensen–Shannon divergence. Sustained divergence — not a rare one-off — degrades that parser's health to degraded, hands more routing weight to tiers 4–5, and triggers the same evolution machinery described above: Drain3 re-mines the drifted traffic, and Needleman–Wunsch sequence alignment tries to transfer the old parser's field labels onto the new template's token positions, producing a v2 draft pack that runs in shadow mode until a human promotes it.

Infrastructure, not just logs

Resource / configuration drift

A second, independent drift signal: is the deployment itself still what was declared, not just the log format.

uli/drift/resource.py compares deployment/desired-state.yaml against observed CPU/memory (psutil) and — when the Docker socket is mounted — container image digests via the Docker Engine API. The shipped template ships with every key commented out, so a fresh deployment produces zero drift events by default; an operator opts in by uncommenting the values that describe their own capacity plan. The observed snapshot is itself content-hashed and written through the same raw store and provenance envelope as ingested logs, so a resource-drift event is forensically traceable to the exact system state that produced it.

A deliberate, stated tradeoff

The Docker socket is not mounted into the api/worker containers in this deployment — giving a container the host socket is close to giving it root on the host, and that wasn't judged worth it for this build. _docker_state() degrades to {} gracefully when the socket is absent (no crash, no false positives) — an operator who wants container-digest drift can mount it explicitly and accept the tradeoff.

Nothing is ever thrown away

Raw provenance and forensic replay

Every normalized event carries a pointer back to the exact original bytes it was built from — byte-for-byte, hash-verified.

The raw store is content-addressed and append-only. Every event in the normalized store carries raw_event_id, raw_segment/offset, and the exact parser_id/version/tier/confidence that produced it. This was verified with a real request against the live stack in this session:

GET /v1/raw/df6c94fbad998c152aec9f8ecb6d71278f58ed87e86bac10573f756d6ad2bb11
→ { "sha256_verified": true, "payload": "raw provenance round trip through the demo script", "parser_id": "engine.drain3", "tier": 4 }

This exact endpoint is where a real production bug was found and fixed during this build (see testing evidence) — worth naming here because it's the clearest proof that "provenance" isn't just a schema field, it's something that was actually exercised end to end over real HTTP until it broke, then fixed, then locked down with a regression test.

Optional, bounded, never load-bearing

The ML sidecar — and why it's tier 6, not tier 1

ULI does not need machine learning to satisfy its core requirement. ML is confined to an optional, fail-open annotation role, only for lines four non-ML strategies already couldn't confidently parse.

Two small, CPU-only, no-pretrained-weights models — an Isolation Forest for per-source anomaly scoring and a nearest-centroid vendor classifier, both training online from local traffic only — run in a separate container (uli-ml) so the primary ingestion path never pays for scikit-learn/numpy unless ML is explicitly enabled (ULI_ML_ENABLED=false by default). Every call is wrapped so a slow or dead sidecar degrades to "tier 6 produces nothing extra," never a stall or an error.

Memory stays flat (single-digit MB delta even at 100K — no leak) and CPU-user time tracks wall time almost 1:1 at every scale — this workload is CPU-bound, not disk/fsync-bound. 1M and 10M runs were not executed: at this rate they would take roughly 94 minutes and 16 hours respectively in this exact unbatched configuration, and projecting a number for them and presenting it as measured would violate the project's own non-fabrication rule for this file.

Profiled, not guessed

Where the CPU time actually goes

The parsing ladder is not the bottleneck. The storage access pattern is.

A cProfile run over 2,000 pipeline.process() calls attributed the majority of cumulative time to SQLAlchemy Core's per-statement machinery — cache-key generation, type coercion, statement compilation — rather than to parsing itself (engine.py:run was 3.0s of an 18.2s total). The proximate cause: a single processed event triggers roughly 9–10 separate SQL execute() calls spread across four write paths (write_event, index_raw, upsert_source, record_unknown) — 19,000 calls for 2,000 events.

Identified, documented, deliberately not fixed in this build

Batching per-event writes into fewer statements is the highest-leverage next optimization. It was not implemented here — the remaining time budget went to completing documentation, deployment verification, and the demo instead of a storage-layer rewrite this late in the build. That is a stated tradeoff, tracked as the top item in what's still pending, not a silently hidden gap.

The actual scaling answer

Horizontal scaling — designed, and actually running

The answer to "how does this scale" is not a faster single process. It's more of them, behind a shared queue.

Deployment topologies

Docker Compose (this build's primary, verified target): docker compose up --build brings up redis + api + worker×2, with --profile ml and --profile collector as opt-in add-ons. All state lives in the uli-data named volume.

Kubernetes (minimal reference manifests, deployment/kubernetes/): namespace, configmaps, a Redis deployment, and API/worker deployments with a shared PVC. Explicitly documented as not production-hardened — no Ingress/TLS/HPA/NetworkPolicy — and with a stated caveat that the default SQLite backend only tolerates a single-node cluster; a real multi-node deployment needs ULI_DB_URL pointed at PostgreSQL (same SQLAlchemy code, dialect switch only — already an optional dependency).

Air-gapped: see § air-gapped operation below.

Two real bugs found and fixed by testing the running system, not mocks

Unknown-vendor gate — the pipeline only recorded unknowns for tiers 6–7, contradicting the documented tiers 4–7 requirement. Found by checking the code against the project's own architecture spec, not just against existing (also-wrong) test expectations.

GET /v1/raw/{id} returned HTTP 500 — a hand-built response bypassed FastAPI's JSON encoder and choked on a raw datetime. Invisible to 43 passing unit tests and the pre-existing integration suite, because none of them exercised this route through real HTTP serialization. Found only by curl-ing the live Docker deployment and reading its logs. Both are fixed, and both are now permanently regression-tested.

Runs with zero outbound network dependency

Air-gapped operation

No log-parsing decision, no model, and no dependency install happens at runtime — everything is baked in at image-build time.

deployment/airgap/build_bundle.sh builds all four images, docker saves them, and packages them with vendor packs, schemas, sample datasets, and docs into one tarball plus a generated LOAD.sh that docker loads everything and brings the stack up with zero network access. The bundle is SHA-256 checksummed for transfer integrity — not yet code-signed (see security posture above; this was corrected in this build rather than left as an inaccurate claim in the README).

Verified in this session: the full compose stack starts and correctly ingests/parses/serves events with no outbound call anywhere in that path. Not verified: a full build→bundle→reload cycle on a genuinely offline second host (the script was syntax-checked, not run end-to-end offline, due to time budget).

Asked directly — answered directly

What's still pending

Nothing here is a surprise buried in code — every item below is also called out in docs/roadmap.md and, where relevant, inline in the section above it.

Highest-leverage, worth doing next

Batch per-event SQL writes. Profiling found ~9–10 individual execute() calls per event across four write paths; batching these is the clearest lever on the measured throughput ceiling (§ where the time goes).

Security

  • Bundle signing (Ed25519) — config fields exist, no implementation.
  • Auth beyond static API keys (OAuth / mTLS / SSO).
  • TLS termination and rate limiting — assumed to be handled by a fronting proxy.

Storage and scale

  • Object-storage raw backend and a ClickHouse analytics adapter — interfaces implied, no adapter written.
  • Kafka/NATS queue backend — only Redis Streams and an in-process queue exist today.
  • An events/sec-vs-worker-count benchmark for the horizontal topology — the topology is verified functionally correct, not throughput-benchmarked.
  • 1M / 10M-event single-process runs — not executed; would take ~94 min / ~16 hr at the measured rate, outside this build's time budget.

ML

  • Model persistence across worker restarts (in-memory only today).
  • An offline precision/recall evaluation harness for anomaly scores.

Detection and deployment

  • Splitting an unknown-vendor cluster that merged two distinct formats via a family-hash collision.
  • Kubernetes API probing for resource drift (only psutil + Docker Engine API are live).
  • Kubernetes manifests are reference-only — no Ingress/TLS/HPA/NetworkPolicy.
  • A full air-gapped build→bundle→reload cycle on a genuinely offline second host.

Deliberately not planned (scope decisions, not gaps)

  • Neural/LLM-based log parsing — evaluated and excluded: higher latency/cost and air-gap friction for a job the deterministic + statistical tiers already handle.
  • Auto-remediation of resource/config drift — the correlator produces evidence for a human, by design, and never acts on its own.
Classified honestly, not oversold

Novelty, scoped honestly

Nothing here claims to be a new algorithm.

Declarative log parsing, Drain3 template mining, Jensen–Shannon drift detection, Needleman–Wunsch sequence alignment, Isolation Forest anomaly scoring, and desired-state-vs-observed infrastructure drift are all established, cited prior art (docs/research.md §1–8). The claimed contribution is narrower: assembling unknown-format handling, parser-drift detection with human-approved evolution, and resource/config drift into one pipeline, with one raw-store/provenance model and one event schema — so an operator sees log-format drift and infrastructure drift correlated on one timeline instead of stitched together from separate tools. That combination, and the hypothesis that template alignment recovers usable field mappings after drift, are flagged as requiring further validation at production scale, not asserted as proven.
